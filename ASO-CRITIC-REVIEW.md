# CRITIC Review: Autonomous Strategy Optimizer (ASO) Design v1

The design has the right ambition, but it currently assumes an optimizer-grade research platform that does not exist yet. The biggest gap is between Sections 1, 3, 5, and 7 and the actual capabilities of `agent/backtest_tool.py`: the design describes multi-asset, risk-aware, optimizer-safe iteration, while the current tool is a lightweight single-symbol declarative tester.

## 1. Architecture gaps

- Section 7 says ASO can reuse the existing `run_backtest` tool, but the current tool only supports one `symbol`, one `interval`, long-only entry/exit rules, and simple percent stop-loss / take-profit. It does not support the Section 1 YAML fields for `universe`, `short`, `filters` as a separate stage, trailing stops, time exits, `max_concurrent_positions`, `cooldown_bars`, or portfolio-level risk. Fix: define an explicit v1 executable subset and reject unsupported YAML fields at compile time, or build a new execution engine before building the optimizer loop.
- Section 3 assumes a rich metrics object, but the existing backtest tool returns only a small summary set: return, Sharpe, max drawdown, trade count, win rate, average trade, best/worst trade, exposure, and buy-and-hold. There is no monthly return series, Sortino, Calmar, Omega, underwater curve, symbol breakdown, or regime breakdown. Fix: add a dedicated metrics pipeline that derives a full equity curve, trade ledger, and benchmark series from each run instead of treating the current `run_backtest` response as optimizer-ready.
- Section 2 defines a closed loop, but it omits the compiler layer between YAML and execution. Right now there is no typed intermediate representation, no semantic validator, and no capability map telling the optimizer which mutations are executable. Fix: insert a `strategy IR -> validator -> executor adapter` stage and make the LLM mutate the IR schema, not raw YAML strings.
- Section 5 calls walk-forward, regime testing, and Monte Carlo "critical," but Section 9 delays those protections until Phase 4 while autonomy arrives in Phase 3. That ordering is backwards. Fix: make robust validation part of the minimum autonomy bar, even if the first autonomous version runs fewer cycles per day.
- Section 6 stores optimizer state in `lineage.json`, `iteration_log.jsonl`, and `lessons_learned.json`. That is fragile for a daemon with retries, concurrent user actions, and crash recovery. Fix: use SQLite or Postgres for state, with immutable backtest artifacts stored separately and referenced by content hash.
- Section 2 does not define selection policy for "next strategy from candidate pool." Without one, the loop will just hill-climb whichever lineage happens to look best early. Fix: add a portfolio of champion-challenger selection rules with explicit exploration budget, novelty scoring, and per-lineage iteration caps.
- Section 2 and Section 3 do not specify data provenance. If OHLCV is revised, missing bars are backfilled, or fee assumptions change, the same strategy version can produce different results later. Fix: persist dataset hash, source, fetch timestamp, fee/slippage model version, executor version, and prompt/model version with every run.
- Section 2 says a cycle takes 30 to 60 seconds and runs every 5 minutes. That is optimistic once you include parent run, child run, OOS validation, regime splits, Monte Carlo, and remote data fetches. Fix: either cache datasets and precompute indicators, or move to asynchronous batched research jobs rather than a fixed five-minute daemon cadence.

## 2. Overfitting risks the 6-layer defense misses

- Section 5 treats the OOS split as a stable validator, but repeated child selection against the same OOS window turns it into training data by another name. Fix: use nested walk-forward or rotating lockboxes, and cap how many times any holdout slice can influence acceptance decisions.
- Layer 2 says "statistically significant" without defining the test. In a many-tries optimizer, vague significance language is how false discoveries get promoted. Fix: use a formal acceptance test such as Deflated Sharpe Ratio, Probability of Backtest Overfitting, or a bootstrap test on the parent-child differential equity curve.
- Layer 2's "beat parent on 3 of 5 metrics" is easy to game because the metrics are correlated and thresholds are arbitrary. A child can win three weakly related metrics while getting worse on what actually matters. Fix: use a single acceptance functional with hard guardrails, for example maximize expected utility or DSR subject to max drawdown, turnover, and trade-count constraints.
- Layer 3's complexity penalty is too naive. Adding one useless indicator is not the same as adding one high-variance branch condition, and some "simple" parameter changes create far more effective degrees of freedom than extra indicators do. Fix: penalize search-space complexity using effective parameter count, branching count, and mutation entropy, not raw indicator/filter counts.
- Layer 4 regime testing is vulnerable to hindsight labeling. If you define bull, bear, and sideways windows after seeing the data, the optimizer will learn your labels, not robustness. Fix: pre-register regime definitions using a fixed external rule set and freeze them before any optimization starts.
- Layer 5 Monte Carlo perturbation of entry timing by plus/minus 2 bars and price by plus/minus 0.1% is too weak for crypto. It will not catch slippage spikes, spread widening, weekend liquidity holes, exchange outages, or funding shocks. Fix: stress the execution model with spread regimes, volatility-linked slippage, missing fills, delayed exits, and temporary data gaps.
- The design misses universe-selection leakage. Section 4 explicitly lets the LLM "modify universe," which means it can data-mine symbols that happened to work in the same history. Fix: separate symbol selection from parameter tuning, and validate added symbols on a disjoint asset holdout or later time slice.
- The design misses survivorship and liquidity bias in crypto. A strategy can look great if dead or illiquid pairs are absent from the research set. Fix: maintain a historical tradable universe by date, with liquidity and minimum notional filters applied at the timestamp of each trade.
- The design misses warm-up leakage around split edges. Indicator history from before the scoring window can bleed information unless handled carefully. Fix: allow warm-up bars for indicator computation but exclude those bars from scoring and make split boundaries explicit in the executor.

## 3. LLM analyst limitations

- Section 4 forces the analyst to identify the "single weakest metric." That is too simplistic for strategies where the real problem is interaction, such as low trade count caused by an over-strict entry plus an over-tight time exit. Fix: let the analyst choose either one weak metric or one coherent failure mode, with up to one bundled hypothesis spanning multiple parameter changes.
- The LLM will fail when the metric signal is weak. With 30 to 50 trades, mixed symbols, or noisy regime dependence, it will still invent a crisp causal story because the prompt demands one. Fix: add a pre-LLM diagnostic gate that can return `INSUFFICIENT_EVIDENCE` and halt mutation if sample quality is poor.
- The LLM cannot reliably reason about executor capability boundaries from prose alone. It will propose YAML mutations that are syntactically valid but semantically unsupported by the current backtester. Fix: constrain generation with schema-aware mutation templates sourced from the compiler's capability matrix.
- Section 4 only feeds the last five iterations plus "lessons learned." That is not enough memory for a long-running optimizer and it biases the model toward recent local minima. Fix: replace recency-only context with retrieval over the full experiment store, clustered by mutation type, failure mode, and market regime.
- The analyst will fail silently when the underlying metrics are corrupted by bad data, benchmark mismatch, or executor bugs. The LLM is not a debugger. Fix: run deterministic diagnostics before every analysis step, including data completeness, benchmark integrity, and strategy sanity checks.
- The convergence rule in Section 4 is fragile. "Sharpe > 2, Sortino > 2.5, drawdown < 10%" can be hit by luck on a short sample, especially in crypto. Fix: define convergence as no material improvement across N accepted iterations plus a robustness pass on unseen data, not just a point estimate threshold.
- The prompt asks for "expected impact" and gives a numerical example. That will encourage unjustified pseudo-precision. Fix: require directional impacts with confidence bands derived from templates, or ban numeric impact claims unless they come from a secondary local sensitivity sweep.

## 4. Strategy YAML expressiveness gaps

- Section 1 lacks boolean composition beyond an implicit AND inside each condition list. There is no OR, NOT, grouping, or nested logic. Fix: represent entry and exit rules as a proper boolean expression tree.
- The YAML cannot express multi-bar or stateful patterns such as "RSI stayed below 30 for 3 bars," "breakout after 20-bar compression," or "only re-enter after one full cooldown cycle following a stop." Fix: add windowed predicates and event/state operators.
- Multi-timeframe logic is an open question in Section 10, but many viable crypto strategies need higher-timeframe trend and lower-timeframe execution. Fix: add a typed multi-timeframe reference model early, or explicitly declare v1 single-timeframe only and block all higher-timeframe mutations.
- There is no execution block. The strategy language does not specify market versus limit versus stop order, bar-close versus next-open execution, maker/taker assumptions, reduce-only, partial fills, or min notional handling. Fix: add an `execution` section that makes these assumptions explicit and testable.
- The risk section is too shallow. `max_position_pct`, `max_drawdown_pct`, and `max_concurrent_positions` are not enough for leveraged or even moderately active crypto trading. Fix: add leverage mode, notional caps, turnover caps, exposure by symbol, and portfolio heat limits.
- The YAML has no cost model. In crypto, fee tier, spread, slippage, and funding often dominate the edge. Fix: add a `costs` section with fee schedule, slippage model, spread assumption, and optional funding/borrow model.
- There is no way to express scale-in, scale-out, partial profit-taking, break-even stop promotion, or rebalance logic. Fix: separate signal generation from position management and make position management its own typed block.
- There is no cross-sectional or portfolio expression. A `universe` list exists, but no ranking, selection, or allocation semantics are defined. Fix: add a portfolio layer for symbol selection, weighting, and correlation constraints instead of overloading single-asset rules.

## 5. Crypto-specific metric concerns

- Section 3 uses thresholds in Section 3.1 that look borrowed from equities and generic CTA lore. For 24/7 crypto strategies, raw Sharpe and win-rate buckets are often misleading unless turnover, fees, and tail risk are normalized. Fix: make thresholds timeframe-aware and cost-adjusted, and calibrate them on crypto-specific distributions.
- The benchmark block uses BTC buy-and-hold and BTC-relative alpha. That is wrong for ETH or SOL-only strategies and actively misleading for multi-asset or market-neutral strategies. Fix: benchmark against cash, symbol-matched buy-and-hold, and an equal-weight universe benchmark; select the benchmark based on strategy type.
- Section 3 lacks tail-risk metrics that matter in crypto: CVaR / expected shortfall, liquidation distance, rolling drawdown by window, time-under-water, realized gap risk, and volatility-of-volatility exposure. Fix: expand the risk block to include left-tail and path-dependent metrics, not just Sharpe-family ratios.
- Trade count thresholds are too crude for crypto. Thirty trades on a 4h strategy over one regime is not equivalent to thirty independent bets. Fix: estimate effective independent observations using holding-time overlap, exposure clustering, and symbol correlation.
- The current metrics do not expose turnover, cost drag, or capacity. A strategy with great gross returns and poor net returns will slip through. Fix: report gross versus net PnL, fee burden as a percent of gross edge, turnover, average trade notional, and liquidity utilization.
- Crypto trades 24/7, so "by hour UTC" and "by day of week" are useful, but the design stops at reporting them. Fix: promote those into diagnostics that can detect exchange-session dependence, weekend fragility, and event-time concentration.
- If the roadmap ever includes perpetuals, funding and basis must be first-class metrics, not an afterthought. Fix: reserve metric slots now for funding PnL, carry exposure, and mark-versus-last-price sensitivity so the schema does not need a breaking redesign later.

## 6. Production failure modes

- Section 2 plus Section 8 assume a daemon can safely mutate strategy state in the background, but there is no concurrency model. A user could promote or edit a strategy while the optimizer is writing a child version. Fix: use transactional updates with optimistic locking and immutable versioned strategy records.
- Section 6 file-based state will corrupt or fork under retries, crashes, or multiple workers. Fix: move mutable state to a database and treat JSON logs as exports, not the source of truth.
- Remote data fetches can fail, return partial candles, or revise recent bars. The current design has no quarantine path, so bad data can produce false "improvements." Fix: add data completeness checks, stale-data detection, retry policy, and run invalidation when source quality fails.
- Model provider drift can change mutation behavior or output schema overnight. Fix: pin model versions for optimizer runs, add output-schema validation, keep a fallback model, and canary any model upgrade on replayed historical iterations.
- Cost control is underspecified. "100 iterations/day" does not help if one iteration fans out into multiple candidate children, regime tests, and Monte Carlo batches. Fix: budget by research credits per evaluation stage and require each cycle to reserve its full downstream validation budget before it starts.
- Notification paths on a message bus will duplicate on retries unless event identity is explicit. Fix: publish idempotent events keyed by run ID and child strategy ID.
- Human approval is necessary but not sufficient. A human can promote a strategy based on stale metrics if the underlying dataset or assumptions changed. Fix: make promotion point to an immutable evaluation artifact with an expiry window and a visible provenance summary.
- The optimizer can get trapped in mutation churn, making tiny changes forever because the prompt says "fix one thing at a time." Fix: add stagnation detection, novelty thresholds, and explicit branch resets that require a larger structural rewrite after repeated local failures.

## 7. What I would change

- Narrow v1 aggressively. Keep Section 1 declarative YAML, but make v1 single-symbol, single-timeframe, long-only, market-entry only, with fixed fee and slippage assumptions. Everything else should be a compile-time error until the executor supports it.
- Add an intermediate Strategy IR. Human YAML should compile into a typed internal representation that the optimizer mutates and the executor consumes. This is the only sane place to enforce capability checks, bounds, and semantic validation.
- Replace the acceptance rule with a formal scorecard. Example: accept only if the child beats the parent on Deflated Sharpe Ratio and net return, while staying within hard limits for max drawdown, turnover, and minimum effective sample size.
- Move walk-forward and lockbox validation into the minimum autonomous version. Regime testing and heavy Monte Carlo can be deferred, but repeated optimization without nested unseen data should not be automated.
- Replace JSON files with SQLite. Store strategies, lineages, runs, artifacts, prompts, outputs, and approval actions in normalized tables; store large blobs like equity curves and trade logs as content-addressed artifacts.
- Put a deterministic diagnostic layer before the LLM. The sequence should be: validate data -> compute metrics -> classify failure mode with rules -> ask the LLM only for bounded mutation proposals within the allowed search space.
- Split optimization into two modes. Use local hill-climbing for parameter tuning and use the LLM only for structural mutations such as adding/removing filters or changing timeframe. That reduces cost and lowers the LLM's chance to hallucinate.
- Add paper-trading shadow validation before candidate promotion. Section 8 already blocks autonomous live trading; go one step further and require a minimum shadow run before a candidate can become "active."
- Add diversity-aware pool management. Accepting only the top Sharpe lineage will converge the whole pool onto one market regime. Keep a small set of orthogonal candidates selected by correlation, turnover profile, and regime behavior.

## 8. What is good and should be preserved

- Section 1's declarative, no-eval strategy representation is the right instinct. It is safer, auditable, and much easier to constrain than freeform code generation.
- Section 4's requirement for structured LLM output is good. Keep the optimizer on a strict schema and reject anything that does not validate.
- Section 5 is directionally right that overfitting needs multiple defenses. The exact layers need work, but the instinct to layer data splits, robustness checks, and iteration memory is correct.
- Section 6's lineage and rationale tracking is valuable. Preserve the idea, but move it onto a transactional store and make artifacts immutable.
- Section 8's approval gates are non-negotiable and should remain. The optimizer should propose; a human should decide what graduates into any trading workflow.
- Section 9's phased rollout is also good in spirit. Preserve the staged delivery model, but reorder it so autonomy comes after the minimum viable statistical safeguards rather than before them.

## Bottom line

The design is strongest when it treats ASO as a research assistant with tight guardrails and weakest when it assumes an autonomous optimizer can be safely layered on top of the current `run_backtest` tool. If you narrow the executor scope, formalize acceptance statistics, freeze data provenance, and move robust validation earlier in the rollout, this becomes a credible system. If you do not, it will mostly optimize noise while generating persuasive explanations for why the noise looks like alpha.
