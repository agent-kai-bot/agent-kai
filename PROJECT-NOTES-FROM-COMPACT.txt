     The architectural design I produced covered:

     **Core mental model:** Three runtime components — `kaid` daemon (owns sessions, sub-agents, signal consumer, market data fanout, persistent stores, WebSocket server), terminal client (thin Textual TUI speaking JSON over WS), web UI client (Svelte SPA
     speaking same protocol).

     **Sessions:** Named conversation contexts. Each owns its chat_history, _input_queue, UI state (chart symbol/timeframe/source/size, watchlist, autotrade flag), per-session AgentRunner instance, persisted to `workspaces/sessions/{name}.json`. Sub-agents,
     memory, skills, market data, signal consumer are shared (NOT per-session).

     **Wire protocol:** JSON over WebSocket. Messages include: client→daemon (attach, input, interrupt, subscribe, unsubscribe, heartbeat), daemon→client (session_attached, token, tool_start, tool_end, final, status, signal, chart_bar, sub_agent_event,
     error). Multi-attach broadcast (all clients on a session see all events).

     **Why WebSocket over gRPC/NATS:** Bidirectional, native browser support, native Python support, streaming-friendly, observable.

     **Backwards compat:** `--terminal` auto-spawns daemon if not running, transparent to current users. `--standalone` is the escape hatch for in-process mode.

     **Web UI stack recommendation:**
     - Backend: FastAPI mounted in daemon, REST endpoints for `/api/sessions`, `/api/agents`, `/api/skills`, `/api/config`, `/api/health`
     - Frontend: Svelte + SvelteKit (NOT Streamlit per user requirement, NOT React)
     - Charts: TradingView Lightweight Charts
     - Styling: Tailwind, dark by default
     - Auth: Bearer token from `workspaces/daemon-token.txt`, localhost-only by default

     **8 open questions for the user** (listed above in pending tasks)

     **Phased rollout (6 phases, ~10-15 days):**
     1. Extract daemon-runnable core (1-2 days)
     2. Terminal becomes daemon client with `--remote` flag (2-3 days)

     6. Polish + auth + systemd unit + CLI script wrappers (1-2 days)

     **Risks table** covering protocol churn, daemon crashes, race conditions, sub-agent shared state, web UI maintenance burden, backwards compat breaks, port conflicts, state sync.

     **What does NOT change:** Agent runtime itself, cloud kai-api gateway, agent-config.json schema, NATS internal bus, sub-agents, slash commands, existing tests.
